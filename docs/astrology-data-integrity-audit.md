# CosmoScope Astrology Data Integrity Audit

## Scope

Focused audit of the current authenticated astrology data path.

This audit does not modify runtime behavior.

Primary question:

Can every visible astrological fact in CosmoScope be traced to AstrologyAPI or deterministic normalization, without frontend invention?

## Executive Verdict

CosmoScope is partially wired to paid AstrologyAPI data, but the current system is not yet at a "proven facts only" beta standard.

The natal chart path is the strongest part of the system. It calls AstrologyAPI's `western_chart_data`, normalizes Sun, Moon, Rising, planets, degrees, birth metadata, and chart accuracy, then caches the result in Supabase.

The forecast path is wired to AstrologyAPI transit endpoints, but visible reading content can still come from deterministic fallback prose, mock provider output, cached legacy strings, or Gemini output depending on Worker environment variables and cache state.

The largest integrity gap is not that the chart is fake. The gap is that visible prose does not currently carry enough provenance for the frontend or QA process to prove which astrological facts powered each sentence.

## Current Runtime Pipeline

### 1. Birth Data Intake

Frontend file:

- `apps/web/app/app/LiveExperience.tsx`

Relevant behavior:

- Signup normalizes birth date into `YYYY-MM-DD`.
- Signup normalizes birth time into `HH:MM`.
- Unknown birth time sends `12:00` plus `unknownBirthTime: true`.
- Birthplace lookup resolves label, latitude, longitude, and timezone.
- Signup sends birth data to the Worker signup route.
- After signup/login, `hydrateMember` calls `/api/chart`, then `/api/forecast`.

Integrity status:

- Good direction.
- The frontend sends exact birth inputs when a selected geocode result exists.
- The frontend passes `timezoneOffset: null`; the Worker recalculates from timezone when needed.

Risk:

- The frontend can still load forecasts from stored chart birth data and does not expose source metadata to the UI.
- A user-facing failure may read like a generic app error rather than a precise data-integrity state.

### 3. Natal Chart Generation

File:

- `worker/src/index.ts`

Relevant path:

- `/api/chart`
- `resolveAstrologyProfileInput`
- `buildAstrologyChartSnapshot`
- `callAstrologyApi`
- `normalizeAstrologyChart`

AstrologyAPI endpoint used:

- `western_chart_data`

Payload fields sent:

- `day`
- `month`
- `year`
- `hour`
- `min`
- `lat`
- `lon`
- `tzone`
- `house_type`

Normalization:

- Sun is read from flattened AstrologyAPI house planets.
- Moon is read from flattened AstrologyAPI house planets.
- Rising is read from first house sign when birth time is known.
- Ascendant degree is read from first house start degree.
- Midheaven degree is read from tenth house start degree.
- Unknown birth time uses `whole_sign` and suppresses Rising.

Integrity status:

- Strong.
- The core natal facts are sourced from AstrologyAPI output and normalized deterministically.
- The cached chart stores `source_version`.
- Chart accuracy metadata says `engine: astrologyapi`, `houses: placidus_from_astrologyapi` or `whole_sign_no_exact_birth_time`, and `planets: western_chart_data`.

Risks:

- Rising sign is inferred from house 1 sign, not from a separately named ascendant field.
- The chart summary is prose generated by deterministic template, not AstrologyAPI.
- The cached chart response merges in a live dominant transit each time, so the chart payload is not purely natal at response time.
- `CHART_SOURCE_VERSION` is only a broad source version, not a full provider/version/input-hash audit record.

### 4. Transit and Forecast Fact Collection

File:

- `worker/src/index.ts`

AstrologyAPI endpoints used:

- `natal_transits/daily`
- `natal_transits/weekly`
- `life_forecast_report/tropical`

Normalization:

- `transit_planet`
- `transit_sign`
- `aspect_type`
- `natal_planet`
- `exact_time`
- `planet_position` for life forecast fallback parsing

Transit priority:

- Outer planets are weighted higher.
- Exactness is scored from `exact_time`.
- Top five transit signals are retained.
- Dominant transit is the first selected signal.

Integrity status:

- Good source connection exists.
- Daily, weekly, and long-range modes all call AstrologyAPI-backed endpoints when `ASTROLOGY_API_KEY` is configured.

Risks:

- The transit prioritization is CosmoScope logic, not AstrologyAPI ranking.
- `orb` is currently set to `0` for transit signals, so orb/exactness evidence is incomplete.
- `inferNatalSignForBody` currently returns the natal body label rather than resolving the natal body's actual sign for most bodies.
- Long-range transits parse `planet_position` strings with a regex and set `transitSign: "current sky"`, which is not a real sign.
- Life forecast prose returned by AstrologyAPI is not preserved as an explicit source field in the final forecast response.

### 7. Reading Generation

File:

- `worker/src/index.ts`

Current behavior:

- `buildForecastContentResult` always builds v1 fallback content first.
- If Reading Engine v2 is disabled, no AI provider is configured, chart is incomplete, or provider generation fails, the system returns deterministic fallback prose.
- If v2 AI is enabled and a provider succeeds, output is validated and rendered.
- Daily v2 output can return `structuredDailyBrief`.
- Weekly/monthly/yearly still return rendered paragraphs.

Worker defaults:

- `READING_ENGINE_VERSION=v1`
- `ENABLE_AI_READINGS=false`
- `AI_READING_PROVIDER=mock`
- `ENABLE_PAID_AI_SMOKE=false`

Integrity status:

- Cost safety is strong.
- Gemini is minimized by default.
- Paid Gemini smoke routes are guarded.

Risks:

- In default Worker config, beta users may see v1 deterministic fallback rather than the intended v2 editorial structure unless production variables differ.
- Mock provider output may be used when enabled.
- The fallback prose includes generic daily/weekly/monthly language that is based on chart/transit context but not fully library-backed.
- Cached content can preserve older formats indefinitely until regeneration rules force refresh.

### 8. Forecast Caching

Files:

- `worker/src/index.ts`

Current cache stores:

- `user_id`
- `timeframe`
- `effective_date`
- `content`

Integrity status:

- Caching exists and is useful for cost control.

Risks:

- Cache does not store structured daily brief.
- Cache does not store interpretation packet.
- Cache does not store editorial brief.
- Cache does not store AstrologyAPI endpoint names, raw transit evidence, provider, fallback state, or input hash.
- Cached daily content has to be reparsed into structured fields.

This is the most important data-integrity gap.

## Highest-Risk Findings

### P0 — Forecast cache lacks provenance

The cache stores only rendered `content`.

This prevents QA from proving, after the fact, which AstrologyAPI endpoint, chart source version, transit evidence, interpretation packet, editorial brief, AI provider, fallback mode, and input birth data generated the visible reading.

Recommended fix:

Add structured cache metadata without changing external client behavior.

Suggested fields:

- `engine_version`
- `provider`
- `fallback_used`
- `chart_source_version`
- `birth_input_hash`
- `astrology_sources`
- `interpretation_packet`
- `editorial_brief`
- `structured_daily_brief`
- `generated_at`

### P0 — Monthly/yearly premium gates conflict with beta canon

The current Worker and frontend still contain premium gating for monthly/yearly forecasts.

The beta canon says:

- no subscriptions
- no memberships
- no locked Daily, Weekly, or Monthly content
- Yearly visible but Coming Soon
- optional tip jar only

Recommended fix:

Before any beta deployment, remove monthly lock behavior and keep yearly as Coming Soon.

### P0 — Interpretation Packet is architecture, not yet a real interpretation manual

The packet exists, but it mostly formats transit facts.

It does not yet use curated aspect/sign/house/domain interpretation records from `docs/interpretation-engine.md` or the editorial libraries.

Recommended fix:

Build the first controlled interpretation table for the major aspect types and transit bodies actually used in production.

Start small:

- conjunction
- opposition
- square
- trine
- sextile
- Mercury
- Venus
- Mars
- Jupiter
- Saturn
- Moon

### P1 — Frontend fallback can invent a generic Your Move

If the daily parser cannot find `**Your move:**`, it supplies:

`Choose one practical action that makes the day easier to move through.`

This is safe in tone, but weak for integrity.

Recommended fix:

Do not fabricate Your Move on authenticated readings. Show a restrained incomplete-reading state or request regeneration.

### P1 — Weekly/monthly are not structured like Daily

Daily has `StructuredDailyBrief`.

Weekly and Monthly are still paragraph-only.

Recommended fix:

Add structured internal weekly/monthly formats while preserving legacy `content`.

### P1 — Long-range transit sign is not factual

`selectTransitSignalsFromLifeForecast` sets `transitSign: "current sky"`.

Recommended fix:

Do not expose that as a sign. Store it as `transitContextLabel` or leave transit sign null.

### P1 — Orb and exactness language needs tightening

Transit `orb` is currently `0`.

Exactness is a local score from exact time proximity, not an orb degree.

Recommended fix:

Do not display orb unless AstrologyAPI provides a real orb or it is calculated deterministically from raw longitudes.

### P2 — Chart summary is deterministic prose, not source metadata

The chart summary reads as interpretive prose but is only a template from bigThree.

Recommended fix:

Either make it visibly introductory or route it through the same interpretation-library system.

## Recommended Next Implementation Pass

### Step 1 — Source Metadata Without UI Change

Extend Worker internals and cache to retain source metadata.

Do not change public API fields yet.

Goal:

QA can inspect a cached forecast and prove exactly what powered it.

### Step 2 — Remove Product-Model Conflict

Align dashboard and Worker behavior with beta canon:

- Daily open.
- Weekly open.
- Monthly open.
- Yearly Coming Soon.
- Tip jar only.

### Step 3 — Lock No-Invention Frontend Rules

Authenticated frontend must never invent astrology or practical action fallbacks.

If structured data is missing:

- render legacy cached content if available
- otherwise show a clear incomplete-reading state
- do not fabricate Notice When or Your Move

### Step 4 — Build Minimal Interpretation Library v1

Create code-controlled mappings for:

- transit body
- aspect
- natal target
- domain
- tension
- opportunity
- observable moments
- allowed actions
- avoid language

This gives CosmoScope voice legitimacy beyond prompt writing.

### Step 5 — Make Daily/Weekly/Monthly Share One Contract

Daily is closest.

Weekly and Monthly should receive structured formats next, while preserving legacy `content`.

## Suggested Beta Gate

Do not call the product beta-ready until this test passes:

For one disposable account:

1. Create account with exact birth date, time, and place.
2. Confirm `/api/chart` response includes `accuracy.engine = astrologyapi`.
3. Confirm Sun, Moon, Rising match AstrologyAPI-normalized chart payload.
4. Confirm Daily, Weekly, and Monthly are generated from the saved chart and current AstrologyAPI transit endpoint.
5. Confirm cache stores source metadata.
6. Confirm the dashboard renders no frontend-invented astrology fallback.
7. Confirm no locked premium language appears in the beta dashboard.
8. Confirm no Gemini request occurs unless explicitly enabled.
9. Confirm `Your Move` comes from structured brief or deterministic engine, not frontend fallback.

## Bottom Line

CosmoScope is close, but not yet integrity-locked.

The foundation is real:

- paid AstrologyAPI chart endpoint is wired
- paid AstrologyAPI transit endpoints are wired
- Supabase chart and forecast caches exist
- Interpretation Packet and Editorial Brief layers exist
- Gemini is constrained and minimized

The risk is not infrastructure absence.

The risk is provenance ambiguity.

The next engineering goal should be simple:

Every visible astrological fact must be traceable, every interpretation must come from controlled meaning, and every prose layer must prove it did not invent the astrology.
